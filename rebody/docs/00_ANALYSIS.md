# ReBody — 착수 문서 분석 리포트

원문: "MetaboReset — MVP 개발 착수 최종본" (Google Play 출시 기준 / 비용 최소화 전략 포함)
분석일: 2026-07-27 · 결론: **전체 방향은 그대로 진행 가능.** 아래 항목만 수정·보강해서 착수했습니다.

## 0. 브랜드 확정 반영

| 항목 | 값 |
|---|---|
| 스토어 등록명 | `ReBody` (콜론 제외 — Play Console·패키지명·도메인에서 `:` 사용 불가) |

기존 코드/문서상의 `MetaboReset`은 전부 `ReBody`로 치환했습니다. 다만 **"대사 리셋(metabolic reset)"이라는 컨셉 자체는 온보딩 카피에 그대로 유지**했습니다. 이름에서 빠진 의미를 카피가 받아주는 구조입니다.

## 1. 사실관계 정정 (원문 기준)

### 1-1. Gemini 모델 — 원문이 맞습니다 (검증 완료)
원문의 `gemini-3.1-flash-lite`는 **2026년 7월 현재 유효한 모델 ID**입니다. "1.5 Flash는 종료됐다"는 지적도 정확합니다.
다만 단가는 원문의 "100만 토큰당 $0.10~0.25"보다 출력 쪽이 높습니다.

| 모델 | 입력 / 출력 (per 1M tokens) | 비고 |
|---|---|---|
| **gemini-3.1-flash-lite** | $0.125 / $0.750 | MVP 기본값으로 채택 |
| gemini-2.5-flash-lite | $0.10 / $0.40 | 더 저렴하나 구세대. 비전 품질 열세 |
| gemini-3.5-flash-lite | $0.30 / $2.50 | 정확도 문제 시 승급 대상 |

**설계 반영:** 출력 단가가 입력의 6배이므로 **출력 토큰을 조이는 게 비용의 전부**입니다.
→ 모든 Gemini 호출에 `maxOutputTokens`를 명시적으로 걸고(음식 인식 256, 스케줄 파싱 512, 주간 피드백 700), `responseMimeType: application/json` + `responseSchema`로 서술형 장문 출력을 원천 차단했습니다. 모델 ID는 하드코딩하지 않고 `GEMINI_MODEL` 환경변수로 뺐습니다 (모델 교체 시 재배포 불필요).

### 1-2. Phase 개수 불일치
"Phase 1 → 8 순차 입력"이라고 써 있지만 실제 정의된 것은 **Phase 1~7**입니다. 8번째는 정의되지 않았습니다.
→ 로드맵에서는 Phase 1~7로 확정하고, `docs/02_ROADMAP.md`에 **Phase 0(법무·정책 선행)** 을 추가했습니다. 이유는 2-1 참조.

### 1-3. Supabase 무료 티어 일시정지
"7일 미접속 시 자동 일시정지" — 맞습니다. 다만 **Supabase Scheduled Functions(pg_cron) 자체가 DB 활동으로 집계되므로**, 원문의 `keepalive-ping` Edge Function은 실제로는 "Edge Function을 깨우는" 용도보다 **DB write가 발생해야 확실**합니다.
→ `keepalive-ping`을 no-op이 아니라 `system_heartbeat` 테이블에 upsert하는 형태로 구현했습니다. no-op이면 정지를 못 막을 수 있습니다.

## 2. 착수 전 반드시 처리해야 할 리스크 (원문 미반영 항목)

### 2-1. ⚠️ 최우선: 건강정보 = 민감정보 (개인정보보호법 제23조)
단식 기록·식사 기록·체중은 국내법상 **민감정보**입니다. 일반 개인정보 동의와 **분리된 별도 동의**가 필요하고, 이걸 안 하면 Play Console 심사가 아니라 **국내 규제 리스크**입니다.
추가로 이 앱은 사진과 건강 데이터를 **Google(Gemini API)로 국외 이전**합니다 → **국외이전 별도 동의(제28조의8)** 가 또 필요합니다.

→ 반영: 온보딩에 3분할 동의 화면(필수 이용약관 / **민감정보 처리 별도 동의** / **국외이전 별도 동의** / 선택 마케팅)을 Phase 0 항목으로 넣고, `consents` 테이블에 동의 시각·버전·IP를 남기도록 스키마를 추가했습니다. 원문 스키마에는 동의 기록 테이블이 아예 없었습니다.

### 2-2. ⚠️ Supabase RLS 미언급 — 원문 스키마 그대로 가면 전체 데이터 유출
원문 Phase 1에 **RLS(Row Level Security) 정책이 한 줄도 없습니다.** Supabase는 anon key가 클라이언트에 그대로 박히는 구조라, RLS 없이 테이블을 만들면 **아무나 남의 식사 사진·건강 기록을 전부 읽을 수 있습니다.** MVP에서 가장 치명적인 구멍입니다.
→ 반영: `20260727000200_rls_policies.sql`에서 전 테이블 RLS 활성화 + `auth.uid()` 기반 정책. Storage 버킷(`meal-photos`)도 사용자 폴더 단위 정책을 걸었습니다.

### 2-3. ⚠️ 스캔 횟수 제한을 클라이언트에서 세면 안 됨
원문 Phase 3의 "free plan 3 scans/day"는 구현 위치가 명시돼 있지 않습니다. 클라이언트에서 카운트하면 앱 재설치·시계 조작으로 무한 우회됩니다 = Gemini 비용이 그대로 샙니다.
→ 반영: `consume_scan_quota()` **Postgres 함수**로 원자적 차감(SECURITY DEFINER, row lock). Edge Function이 Gemini를 호출하기 **전에** 이 함수를 먼저 호출하고, 실패 시 402를 반환합니다. 클라이언트 카운터는 표시용일 뿐입니다.

### 2-4. ⚠️ 섭식장애 안전장치 부재 (Play 정책 + 윤리)
단식 앱은 Google Play의 민감 카테고리입니다. 저체중 사용자에게 장시간 단식을 권하는 앱은 **정책 위반 + 실질적 위해** 소지가 있습니다.
→ 반영:
- 온보딩에서 만 18세 미만 차단, 임신·수유 중 차단
- BMI < 18.5 사용자는 단식 스케줄 생성을 막고 안내 화면으로 분기 (`src/domain/safety.ts`)
- 24시간 초과 단식 타깃 하드 캡
- AI 피드백 프롬프트에 "칼로리 추가 제한·체중 감량 가속을 절대 권하지 말 것" 제약을 시스템 지시로 고정
- 앱 내 상시 의학적 면책 고지 + 상담 안내

### 2-5. `food_nutrition_cache` PK 설계 결함
원문: `food_name_normalized text primary key`.
"닭가슴살"은 조리법·브랜드·출처(MFDS vs AI추정)에 따라 값이 다릅니다. 단일 PK면 **AI 추정치가 공식 데이터를 덮어씁니다.**
→ 반영: PK를 `(food_name_normalized, source)` 복합키로 변경. 조회 시 `mfds_db` 우선. 원문 컬럼(`sodium_mg` 등)은 유지하고 `fiber_g`, `serving_size_g`, `hit_count`를 추가했습니다.

### 2-6. `schedule_overrides` 유니크 제약 누락
`(pattern_id, override_date)`에 유니크가 없으면 같은 날짜 오버라이드가 중복 생성되어 "오늘 스케줄"이 비결정적이 됩니다.
→ 반영: `UNIQUE (pattern_id, override_date)` + `ON CONFLICT DO UPDATE` 업서트.

### 2-7. 타임존 — 교대근무 앱의 핵심 버그 원천
원문 Phase 2의 "overnight shifts (work_end past midnight)"는 맞게 짚었지만, **저장 형식이 정의돼 있지 않습니다.** 야간 22:00~06:00 근무를 UTC 타임스탬프로 저장하면 "cycle day index"가 하루씩 밀립니다.
→ 반영 원칙:
- `schedule_cycle_days`의 시각은 **`time` (벽시계, TZ 없음)**, 날짜는 **`date` (civil date)** 로만 저장
- 사이클 인덱스 계산은 **순수 civil-date 정수 연산** → TZ 무관, Deno/RN 양쪽 동일 결과
- 벽시계 → 절대시각(instant) 변환은 **앱 레이어에서만** `users.timezone`(기본 `Asia/Seoul`)으로 수행
- ICS 내보내기는 변환 자체를 하지 않고 `TZID=Asia/Seoul` + 로컬 시각으로 발급 (변환 버그 원천 제거)
- 자정 넘김은 `work_end <= work_start`면 `crossesMidnight = true`로 판정, 종료일을 +1일

### 2-8. FCM HTTP v1 인증
원문 Phase 5의 "Edge Function `send-push` calling FCM HTTP v1 API"는 맞지만, v1은 **레거시 서버 키가 아니라 서비스 계정 JWT → OAuth2 access token** 이 필요합니다. Deno에서 직접 RS256 JWT를 서명해야 합니다.
→ 반영: `_shared/fcm.ts`에 서비스 계정 JWT 서명 + 토큰 캐싱(55분) 구현. 서버 키 방식은 이미 종료됐습니다.

### 2-9. RevenueCat은 Expo Go에서 동작하지 않음
`react-native-purchases`는 네이티브 모듈입니다. Expo Go로는 테스트 불가 → **development build 필수**이고, Play Console에 앱이 올라가 **내부 테스트 트랙에 최소 1회 배포된 뒤에야** 인앱상품이 조회됩니다.
→ 반영: Phase 6은 Play Console 등록($25 결제) 이후로 순서 고정. 그 전까지 `purchases.ts`는 mock 모드로 동작하도록 분기했습니다.

### 2-10. EAS Build 무료 한도
"월 15회"는 시점에 따라 변합니다(현행 무료 플랜은 그보다 타이트할 수 있음). 원문의 전략 자체(OTA 우선, 네이티브 변경 시에만 빌드)는 옳으므로 유지하되, **한도는 착수 시점에 EAS 대시보드에서 재확인**해야 합니다. 문서에 숫자를 못 박지 않았습니다.

## 3. 팀장 코멘트에 대한 의견 — 동의, 다만 한 단계 더 앞으로

> "Phase 3(푸드 스캐너) 프로토타입 검증을 Phase 2 완료 직후 최우선으로"

**동의합니다. 그리고 Phase 2보다도 먼저 할 수 있습니다.**

푸드 스캐너 정확도 검증에는 앱도, 스케줄 엔진도, 로그인도 필요 없습니다. 필요한 건 **한식 사진 30~50장 + Edge Function 하나**뿐입니다. 스케줄 온보딩(Phase 2)은 UI 작업량이 큰데, 그걸 다 만들고 나서 "AI가 한식을 못 알아본다"는 걸 알게 되면 손실이 훨씬 큽니다.

→ 반영한 실행 순서:

```
Phase 1 (인프라)
   └─> Phase 3a: 스캐너 정확도 스파이크  ← 여기서 Go/No-Go 판단
         │  한식 사진 50장 골든셋 → analyze-food-image 호출
         │  합격선: 음식명 top-1 정확도 ≥ 70%, MFDS 매칭률 ≥ 60%,
         │          칼로리 오차 ±25% 이내 비율 ≥ 70%
         ├─ 합격 → Phase 2 → Phase 3b(UI) → 4 → 5 → 6 → 7
         └─ 불합격 → 모델 승급(3.5 Flash) 또는
                     "사진 스캔"을 "텍스트 검색 + 사진 보조"로 피벗
```

골든셋 평가 스크립트를 `scripts/eval-food-scanner.ts`로 같이 넣었습니다. 판단 근거를 감이 아니라 숫자로 남기기 위한 것입니다.

**한 가지 더 짚자면**, 이 앱의 진짜 차별점은 스캐너가 아니라 **"교대근무 사이클을 이해하는 스케줄링"** 입니다. 푸드 스캐너는 이미 시중에 많고 정확도로 이기기 어렵습니다. 반면 3교대 사이클 기반 단식 스케줄링은 경쟁 앱(Zero, Fastic 등)에 사실상 없습니다.
→ 그래서 스캐너 검증에서 불합격이 나와도 **프로젝트를 접을 이유는 아닙니다.** 스캐너를 보조 기능으로 격하하고 스케줄링에 집중하는 피벗이 정답에 가깝습니다. Go/No-Go의 대상은 "프로젝트"가 아니라 "스캐너의 위상"입니다.

## 4. 비용표 정정

원문 비용표는 대체로 정확합니다. 두 가지만 수정합니다.

| 항목 | 원문 | 정정 |
|---|---|---|
| Gemini 단가 | $0.10~0.25 / 1M | 입력 $0.125 / **출력 $0.750** — 출력 토큰 제어가 비용의 핵심 |
| 필수 고정비 | $25 (Play 등록) | $25 유지. 단 **공공데이터포털 API 키 발급(무료, 승인 1~2일)** 이 크리티컬 패스에 있음 → 착수 즉시 신청 |

MVP 트래픽(DAU 100, 1인 3스캔) 기준 실측 추정: 캐시 히트율 50% 가정 시 **Gemini 월 $1~3 수준.** 원문 결론("$25 외 사실상 무료")은 유지됩니다.
