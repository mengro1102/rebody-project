## 0. 왜 두 트랙으로 나누는가

**비용 때문이 아닙니다.** 이 프로젝트의 실제 지출은 아래가 전부입니다.

| 구간 | 실제 비용 |
|---|---|
| Play 개발자 등록 | **$25** (1회, 계정당) |
| 테스트 전 구간(12명 × 14일 포함)의 Gemini 호출 | **$0.2 미만** — 무료 티어 안에서 끝남 |
| Supabase · FCM · MFDS · RevenueCat · Crashlytics | **$0** |
| 출시 후 DAU 100 기준 | **월 $2 수준** |

즉 **비용은 의사결정 변수가 아닙니다.** 그런데도 나눠야 하는 이유가 세 가지 있습니다.

**① Google이 강제하는 14일 대기가 존재합니다 (이번 검토의 최대 발견)**

2023-11-13 이후 만든 **개인(personal) 개발자 계정**은 프로덕션 출시 전에
**12명 이상의 실제 테스터가 14일 연속으로 opt-in한 비공개 테스트**를 완료해야 합니다.
- "opt-in"은 초대 수락 + **실제 설치**까지를 의미합니다. 초대만 보낸 인원은 계산되지 않습니다.
- 12명이 **같은 14일 창에 겹쳐** 있어야 합니다. 7일차에 1명이 이탈하면 **카운터가 초기화**됩니다.
- 통과 후 프로덕션 접근 신청 → 심사 **약 7일**.

→ 이 구간은 코드로 단축할 수 없는 **순수 달력 시간 최소 3주**입니다.
개발 트랙과 섞어두면 "언제 시작해야 하는지"가 보이지 않습니다. **분리해서 최대한 일찍 착수해야 하는 구간**입니다.

**② 되돌릴 수 없는 결정이 배포 트랙에만 모여 있습니다**

계정 유형, 패키지명, Supabase 리전, 구독 상품 ID — 전부 나중에 못 바꿉니다.
개발 트랙은 언제든 되돌릴 수 있습니다. 성격이 다른 작업을 같은 목록에 두면 판단이 흐려집니다.

**③ 1인 개발이라 컨텍스트 전환 비용이 가장 비쌉니다**

"코드 쓰는 날"과 "폼 채우고 승인 기다리는 날"은 다른 종류의 일입니다.
개발 트랙은 혼자, 오프라인으로, 승인 없이 끝까지 갈 수 있게 설계했습니다.

```
개발 트랙 (D)  — 돈·승인·타인 불필요. 혼자 끝까지 간다.
  D1 레포·툴체인 ✅ → D2 앱 셸 ✅ → D3 포지셔닝 확장 ✅ → D4 백엔드 배포·검증

  R0 계정 개설 ← 오늘 시작   → R1 1인 검증 → R2 내부 테스트 → R3 화이트리스트 12명×14일
                                                                    → R4 프로덕션 승인 → R5 단계 출시
```

**두 트랙의 합류 지점**

| 배포 단계 | 시작 조건 (개발 트랙에서) |

(첫 끼 = 기상 +1시간, 창 길이는 프리셋별).

### 시차 대응은 프리셋이 아니라 타임존 전환이 본체입니다

스케줄이 벽시계로 저장돼 있어서, 도착지에서 **시간대만 바꾸면** 현지 시각 기준으로 그대로 재배치됩니다.
사용자가 실제로 갈리는 지점은 "어느 쪽 시각에 맞출 것인가"이고, 이건 물어봐야 합니다.

| 모드 | 동작 | 쓰는 경우 |
|---|---|---|
| **현지 시각에 맞추기** | 시간대만 변경. "아침 8시 첫 끼"가 도착지 8시가 됨 | 대부분의 출장·이주 |
| **한국 시각 유지하기** | 벽시계 값을 오프셋 차이만큼 이동. 먹는 **절대 순간**이 그대로 | 2~3일 짧은 출장 |

선택 전에 "첫 끼가 현지 몇 시가 되는지"를 미리 보여줍니다. 사이클 인덱스에는 타임존을 끌어들이지
않았습니다 — 여기서 섞으면 하루가 밀립니다.

**이연한 것**: 이동일에 창을 점진적으로 미는 자동 시차 적응(예: 하루 1시간씩 이동)은 넣지 않았습니다.
효과에 대한 근거가 약하고, 잘못 밀면 오히려 리듬을 깨뜨립니다. 실제 출장 사용자 피드백을 R3에서
받아본 뒤 판단하는 편이 낫습니다.

### D4-8. MFDS 실호출 — 가장 조용히 크게 틀릴 수 있는 지점

```bash
MFDS_SERVICE_KEY=<재발급 키> npx tsx scripts/probe-mfds.ts 김치찌개
```

12개 필드를 `OK`/`MISS`로 자동 검증합니다. `MISS`가 하나라도 있으면 그 출력을 저에게 주세요 — `FIELD_MAPS`를 맞추겠습니다.
`SERVING_SIZE`가 `"100g"` 형태인지 함께 확인. 이 값이 모든 영양소의 분모입니다.

> 매핑이 어긋나면 **에러 없이 0kcal이 저장**됩니다. "동작하는 것처럼 보이는데 값이 다 0"이 가장 잡기 어렵습니다.

### D4-9. RLS 실측 — 코드 리뷰로 대체하지 마세요

계정 A로 식사 기록 저장 → 계정 B로 로그인 → `meal_logs` 조회 → **A의 기록이 보이면 즉시 중단.**

### D4-11. 전역 비용 상한 — 수익화 철회로 새로 필요해진 것

사용자당 3회/일 제한은 **사용자 수가 늘면 총액을 막지 못합니다.** 매출이 없으므로 총액에 천장이 필요합니다.

| 항목 | 값 |
|---|---|
| 전역 일일 호출 상한 | 2,000건/일 (월 최대 약 $21, DAU 660명까지 흡수) |
| 80% 도달 | 운영자에게 알림 |
| 100% 도달 | **스캐너만 격하** — "지금은 사진 분석이 붐벼요. 음식 이름으로 기록해 주세요" |
| 타이머·스케줄·리포트 | 영향 없음 (AI를 쓰지 않음) |

중단이 아니라 **격하**여야 합니다. 스캐너가 막혀도 텍스트로 기록은 계속돼야 이탈하지 않습니다.
구현: `analyze-food-image`가 `consume_scan_quota()` 호출 **직전**에 전역 카운터를 확인.
마이그레이션 1건(일일 집계 테이블 + 원자적 증가 함수)이 필요합니다. **제게 넘기시면 됩니다.**
