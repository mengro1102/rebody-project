## 0. 왜 두 트랙으로 나누는가

**비용 때문이 아닙니다.** 이 프로젝트의 실제 지출은 아래가 전부입니다.

| 구간 | 실제 비용 |
|---|---|
| Play 개발자 등록 | **$25** (1회, 계정당) |
| 테스트 전 구간(12명 × 14일 포함)의 Gemini 호출 | **$0.2 미만** — 무료 티어 안에서 끝남 |
| Supabase · FCM · MFDS · RevenueCat · Crashlytics | **$0** |
| 출시 후 DAU 100 기준 | **월 $2 수준** |

즉 **비용은 의사결정 변수가 아닙니다.** 그런데도 나눠야 하는 이유가 세 가지 있습니다.

**① Google이 강제하는 14일 대기가 존재합니다 (이번 검토의 최대 발견)**

2023-11-13 이후 만든 **개인(personal) 개발자 계정**은 프로덕션 출시 전에
**12명 이상의 실제 테스터가 14일 연속으로 opt-in한 비공개 테스트**를 완료해야 합니다.
- "opt-in"은 초대 수락 + **실제 설치**까지를 의미합니다. 초대만 보낸 인원은 계산되지 않습니다.
- 12명이 **같은 14일 창에 겹쳐** 있어야 합니다. 7일차에 1명이 이탈하면 **카운터가 초기화**됩니다.
- 통과 후 프로덕션 접근 신청 → 심사 **약 7일**.

→ 이 구간은 코드로 단축할 수 없는 **순수 달력 시간 최소 3주**입니다.
개발 트랙과 섞어두면 "언제 시작해야 하는지"가 보이지 않습니다. **분리해서 최대한 일찍 착수해야 하는 구간**입니다.

**② 되돌릴 수 없는 결정이 배포 트랙에만 모여 있습니다**

계정 유형, 패키지명, Supabase 리전, 구독 상품 ID — 전부 나중에 못 바꿉니다.
개발 트랙은 언제든 되돌릴 수 있습니다. 성격이 다른 작업을 같은 목록에 두면 판단이 흐려집니다.

**③ 1인 개발이라 컨텍스트 전환 비용이 가장 비쌉니다**

"코드 쓰는 날"과 "폼 채우고 승인 기다리는 날"은 다른 종류의 일입니다.
개발 트랙은 혼자, 오프라인으로, 승인 없이 끝까지 갈 수 있게 설계했습니다.

## 1. 전체 지도

```
개발 트랙 (D)  — 돈·승인·타인 불필요. 혼자 끝까지 간다.
  D1 레포·툴체인 ✅ → D2 앱 셸 → D3 포지셔닝 확장 → D4 백엔드 배포·검증
                                                        └→ D5 스캐너 게이트 → D6 안정화

배포 트랙 (R)  — 승인 대기·타인 관여·되돌리기 어려움
  R0 계정 개설 ← 오늘 시작   → R1 1인 검증 → R2 내부 테스트 → R3 화이트리스트 12명×14일
                                                                    → R4 프로덕션 승인 → R5 단계 출시
```

**두 트랙의 합류 지점**

| 배포 단계 | 시작 조건 (개발 트랙에서) |
|---|---|
| R1 (1인 검증) | D2 완료 — 앱이 실행되어야 함 |
| R2 (내부 테스트) | D3 + D4 완료 — 남이 봐도 되는 최소 완성도 |
| R3 (화이트리스트) | D6 완료 — **14일 카운터가 리셋되면 안 되므로 여기서 품질이 필요** |
| R5 (단계 출시) | D5 판정 확정 |

**전체 기간 감각**: 개발 트랙 실작업 1.5~2주 + 배포 트랙 달력 대기 3~4주. 두 트랙이 겹치므로 **총 4~5주**.

### D4-8. MFDS 실호출 — 가장 조용히 크게 틀릴 수 있는 지점


- 그래서 **15~16명을 모집**해 이탈 버퍼를 두는 게 표준적인 대응입니다.

> **14일을 낭비로 보지 마세요.** 1인 개발에서 타인의 실사용 데이터를 얻는 유일한 구간입니다.
