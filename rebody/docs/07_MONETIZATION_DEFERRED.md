# 수익화 보류 — 결정 기록과 복원 런북

결정일 2026-07-29 · 상태 **적용 완료**

---

## 1. 결정

**복무 기간 중 ReBody는 무료로만 배포한다.** 인앱 결제·구독·광고·제휴 커머스·B2B 유료 리포트를
전부 도입하지 않는다.

**근거**: 운영자가 전문연구요원으로 병역을 이행 중이며, 복무 기간 중 사업자등록 및 영리 활동은
편입 취소 리스크가 있다고 판단했다. 이는 운영자의 결정이며 이 문서는 그 결정을 코드와 계획에
반영한 기록이다. (법령 해석 자체는 이 문서의 범위가 아니다. 판단이 필요하면 병무청·지정업체
담당 부서에 확인할 것.)

**Play Console 계정**: 개인 개발자 계정 (ID `4823628915853066077`), $25 결제 완료.

---

## 2. 사실 정정 두 가지

### 2-1. 비공개 테스트 인원은 **12명**입니다 (20명 아님)

Google은 **2024-12-11**에 신규 개인 계정의 비공개 테스트 요건을 **20명 → 12명**으로 완화했습니다.
14일 연속이라는 조건은 그대로입니다.

- 근거: [Play Console 고객센터 — 신규 개인 개발자 계정의 앱 테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465)
- 8명을 덜 모아도 됩니다. 다만 **이탈 버퍼**를 고려해 15~16명 모집을 권장하는 것은 그대로입니다
  (12명이 같은 14일 창에 겹쳐 있어야 하고, 중간 이탈 시 카운터가 초기화됩니다).

### 2-2. 개인 계정이라서 수익화를 못 하는 것은 아닙니다

개인 개발자 계정으로도 유료 앱·인앱 결제는 가능합니다. 조직 계정이 반드시 필요한 것은
**12명×14일 테스트 면제**이지 결제 기능이 아닙니다.

즉 이번 보류의 실제 이유는 **계정 유형이 아니라 복무 신분**입니다. 이 구분이 중요한 이유:
복무 종료 후 수익화를 되살릴 때 **계정을 새로 만들 필요가 없습니다.** 지금 계정을 그대로 쓰면서
판매자 등록만 추가하면 됩니다. (수익 발생 시점의 사업자등록·세무 처리는 별도 영역입니다.)

## 3. 지금 적용된 변경

### 코드

| 위치 | 변경 |

| `docs/04_PRIVACY_POLICY.md` | "유료 구독 관리" 처리 목적 삭제, RevenueCat 수탁자 항목 삭제 |

> 환경변수가 아니라 **소스 상수**로 잠근 것이 핵심입니다. 빌드 프로필을 잘못 만져서
> 결제 UI가 켜지는 사고를 구조적으로 막습니다.

**삭제하지 않고 남긴 것**: `src/features/billing/purchases.ts`, `src/screens/PaywallScreen.tsx`,
`user_subscriptions` 테이블, 페이월 퍼널 Analytics 이벤트. 전부 동작하는 상태로 보존돼 있으며
`MONETIZATION_ENABLED`만 켜면 되살아납니다. 지우면 나중에 다시 만드는 비용이 그대로 발생합니다.

### 계획

- **배포 트랙 R2에서 결제 연동 6개 항목 제거** (구독 상품 등록, RevenueCat 연결, Entitlement,
  웹훅 Edge Function, 라이선스 테스터 결제 검증). Play Console에는 **"인앱 구매 없음"** 으로 신고.
- RevenueCat 웹훅 수신 Edge Function은 **작성하지 않습니다** (기존 계획의 R2-8 철회).

## 4. 스캔 쿼터는 유지합니다 — 목적이 바뀝니다

| | 이전 | 지금 |
|---|---|---|
| 하루 3회 제한의 목적 | 유료 전환 유도 | **비용 방어** |
| 초과 시 안내 | "Pro로 업그레이드" | "왜 제한이 있는지" 설명 + 내일 리셋 안내 |
| 서버 강제 여부 | 필요 | **더 필요해짐** |

수익이 0이므로 Gemini 호출 비용은 **전액 개인 부담**입니다. 제한을 푸는 것은 이제
"매출 기회를 놓치는 일"이 아니라 "청구서를 키우는 일"입니다. `consume_scan_quota()`의
서버 강제는 그대로 두고, 아래 전역 상한을 추가로 넣어야 합니다.

---

## 5. 새로 필요해진 것 — 전역 비용 상한 (D4-11)

사용자당 3회/일 제한만으로는 **사용자 수 자체가 늘어날 때** 비용이 선형으로 증가합니다.
개인 부담이므로 총액에 천장이 필요합니다.

```
사용자당 제한 (기존)  : 3 스캔/일 · consume_scan_quota()
전역 제한   (신규)    : N 스캔/일 · 전체 사용자 합계
```

권장 설계:

| 항목 | 값 | 근거 |
|---|---|---|
| 전역 일일 호출 상한 | **2,000건/일** | 월 최대 약 $21. DAU 660명까지 정상 흡수 |
| 80% 도달 시 | 운영자에게 알림 | 상한에 닿기 전에 인지 |
| 100% 도달 시 | 스캐너만 일시 중단 | "지금은 사진 분석이 붐벼요. 음식 이름으로 기록해 주세요" |
| 그 외 기능 | 영향 없음 | 타이머·스케줄·리포트는 AI를 쓰지 않는다 |

**중단이 아니라 격하(degrade)여야 합니다.** 스캐너가 막혀도 텍스트 입력으로 기록은 계속돼야
사용자가 이탈하지 않습니다. 이건 D3의 포지셔닝과도 맞습니다 — 이 앱의 본체는 스캐너가 아니라
스케줄링입니다.

구현 위치: `analyze-food-image` Edge Function이 `consume_scan_quota()` 호출 **직전**에
전역 카운터를 확인. 새 마이그레이션 1건(일일 집계 테이블 + 원자적 증가 함수)이 필요합니다.

(리텐션이 증명되지 않은 앱에 결제를 붙이면 이탈만 앞당깁니다).

## 7. 복무 종료 후 복원 런북

순서대로 하면 됩니다. 예상 소요 반나절.

1. **`src/lib/env.ts`의 `MONETIZATION_ENABLED`를 `true`로.** 이것만으로 페이월 화면·
   설정의 업그레이드 진입점·스캐너의 "Pro 알아보기"가 동시에 살아납니다.
2. `eas.json`의 preview·production 프로필 `EXPO_PUBLIC_BILLING_MODE`를 `live`로.
3. Play Console → 결제 프로필(판매자) 등록. **계정을 새로 만들 필요 없습니다.**
4. 구독 상품 등록: `rebody_pro_monthly`, `rebody_pro_annual`.
5. 내부 테스트 트랙에 1회 배포 — 이게 있어야 인앱상품이 조회됩니다.
6. RevenueCat 프로젝트 생성 → Play 서비스 계정 키 업로드 → Entitlement `pro` 매핑.
7. **RevenueCat 웹훅 → `user_subscriptions` 갱신 Edge Function 신규 작성** (아직 없는 유일한 코드).
8. `docs/04_PRIVACY_POLICY.md`에 결제 수탁자·처리 목적 복원 후 **개정 고지**.
9. Play Console Data Safety를 "인앱 구매 있음"으로 갱신.
10. 라이선스 테스터로 결제 → 복원 → 해지 전 과정 검증.

동시에 검토할 것: 사업자등록·세무 처리, B2B 체육관 리포트, 제휴 커머스(V2 이연 항목).

## 8. 이 결정이 바꾸지 않는 것

- 개발 트랙 D1~D6 — 그대로입니다. 무료든 유료든 앱은 동작해야 합니다.
- 배포 트랙 R0·R1·R3·R4·R5 — 그대로입니다. 12명×14일 테스트는 무료 앱에도 적용됩니다.
- 안전장치·동의·RLS·데이터 삭제 — 수익과 무관한 법적 요구사항입니다.
- **스캐너 Go/No-Go 게이트(D5)** — 오히려 더 중요해졌습니다. 정확도가 낮으면 비용만 나가고
  가치는 없는 기능이 됩니다. NO-GO 판정 시 격하 결정을 미루지 마세요.
